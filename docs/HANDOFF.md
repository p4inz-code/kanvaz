# Kanvaz — Session Handoff

*For a fresh Claude session picking this project up. Read this first.*

## What Kanvaz is

Kanvaz is an Electron desktop app — a visual reference-board tool ("Reference Operating System") for VFX/3D artists and creative studios, built by Atharva Patil (Northbyte Studios). Repo: `p4inz-code/kanvaz`. Current shipped version: **v5.3.0** (tagged, pushed, published — genuinely was the finish line for that arc, per its own CHANGELOG entry). **v6.0.0 is implemented and validated in this working copy, not yet released — development has reopened.** The user ran a full market analysis against PureRef and every major competitor in this space and asked for one more, deliberately final arc that beats PureRef comprehensively and leaves Kanvaz needing no attention for 2 years. `docs/ROADMAP.md`'s new "The v6.x arc" section (added this session, right after the v5.3.0 historical record) is the authoritative current plan: three pillars (Live Reference, Never Lose Anything Again, Wide-Open Plugin Ecosystem) plus a final dedicated UI-polish pass. v6.0.0 is the first slice of Pillar 1 only — see below. The user separately asked about integration angles with their other project, Mink (a compiled language, Rust-based, Windows-only) — assessed as not worth pursuing technically (different domains, no shared interface), told to the user directly, not written into the roadmap; a separate strategy report was written for Mink's own trio-positioning question, unrelated to Kanvaz.

Core identity, non-negotiable: **100% offline by default. No accounts. No telemetry.** The network calls anywhere in the app are user-initiated and disclosed, never automatic: "Check for updates"; "Browse Official Plugins" (fetches a small catalog JSON) plus the one-time download when you choose to install from it (4.4.0); and, as of **5.0.0**, a URL card's own "Fetch preview" button (title/thumbnail for one specific link, only on click, never on paste/type/load — see SECURITY.md). Any future feature that touches the network must stay narrow, opt-in, and explicitly disclosed in the About screen / README / SECURITY.md — never silent. MCP Bridge (4.4.0's flagship plugin, whole-app-scope as of 4.5.0) is local-IPC-only, not a network feature at all — see below.

## Where things stand technically

- **Plugin system (v4.2.0+)** is the newest architectural layer: `window.KanvazPluginAPI` lets a plugin register card types, full themes, and Settings panels. Convention-based sandbox (plugin JS runs in the same page context, not iframe-isolated) — disclosed, not hidden. Native OS `dialog.showMessageBox` consent gate on install/permission-escalation, enforced in the main process only.
- **Two official plugins** ship as separate release assets, not bundled into the base installer: Theme Creator (`kanvaz-theme-creator-4.4.0.zip`, 4.2.0) and MCP Bridge (`kanvaz-mcp-bridge-4.4.0.zip`, 4.4.0 — see below).
- **File format**: `.kanvaz` is a zip container (`board.json` + per-asset files with SHA-256 hashes) since v4.1.0. Old plain-JSON files still open fine.
- **v4.2.1** was a full-stack audit + hardening pass (data-loss bugs, plugin robustness, security, shortcut bugs, UI-copy-vs-reality corrections).
- **v4.2.2** was a design-consistency + reliability polish pass: unified radius/shadow/animation across every panel and dialog, emoji→SVG icon replacement, native connection-type color palette, fixed Top Mode's drag-bar vanishing mid-drag, fixed Map View connections drifting after window resize.
- **v4.3.0 (shipped)** — Command Palette (Ctrl+K, `src/commands.js`), `KanvazPluginAPI.registerCommand`/`.on(event, handler)`, and the read-only Runtime Data API (`getCards`/`getSelected`/`getConnections`/`getActiveBoard`). `shortcut` shown per palette row is a display hint only — actual key handling still lives in `shortcuts.js`'s dispatcher, unchanged. Full details in `CHANGELOG.md`.
- **v4.4.0 (implemented this session, not yet released)** — Plugin Ecosystem: Hardening, Distribution & MCP Bridge, per `docs/ROADMAP.md`'s v4.4.0 spec:
  1. **MCP Bridge** (`official-plugins/mcp-bridge`) — a local MCP server exposing the active board (list/get/create/update/delete/tag cards, add a reference from a path or URL, search, connections). Off by default, three separate opt-ins required (install → approve → enable in Settings). Transport: a named pipe (Windows) / Unix domain socket (macOS/Linux) that Kanvaz's main process listens on — never a TCP port — plus a standalone `server.js` (plain Node, `@modelcontextprotocol/sdk`) that the AI client itself spawns over real MCP stdio and which forwards tool calls into that local pipe. Every tool handler (`official-plugins/mcp-bridge/main.js`) calls the same `KanvazCards`/`KanvazConnections` functions the UI uses, so every AI-driven change is undo-reversible by construction. A card's `dataUrl` is stripped to a `hasMedia` boolean before crossing the bridge (`sanitizeCard()`).
  2. **Real per-plugin permission enforcement** — new `server` permission (plugin-loader.js); `KanvazPluginLoader` now injects plugins ONE AT A TIME (was: all at once, no waiting) and points `window.KanvazPluginAPI` at a scope built for whichever plugin is currently loading (`buildScopedAPI()` in plugin-api.js) — a gated namespace (`mcpBridge`, today's only one) is genuinely absent unless declared+approved. **A real bug shipped in an early draft of this and was caught by testing, not code review**: a classic-script top-level `var X = ...` binding IS `window.X`, not an independent reference to it, so the original "restore the full API" step was reassigning `window.KanvazPluginAPI` back to whatever the bare `KanvazPluginAPI` identifier currently resolved to — which, after the loop, was the LAST plugin's own scoped object, not the true base one. Fixed by capturing a `baseAPI` local inside `KanvazPluginLoader`'s own closure, never itself the target of a `window.KanvazPluginAPI = ...` assignment. `test/plugin-scope-test.js` (real headless Chromium) asserts this exact scenario now and is a permanent regression guard, not a one-off script.
  3. **CI packaging** (`.github/workflows/build.yml`) — zips each `official-plugins/*` folder and uploads to the tag's GitHub Release, one matrix leg only (ubuntu-latest).
  4. **"Browse Official Plugins"** (Settings → Plugins) — fetches `official-plugins/catalog.json` (committed to this repo, served via raw.githubusercontent.com) through a new main-process-only IPC handler (`catalog-fetch`) so no new CSP `connect-src` host becomes fetchable from the renderer; installs via `plugins-install-from-catalog` (downloads a `github.com`-only-allowlisted zip, extracts with a zip-slip path guard), then reuses the existing Review & Enable consent flow unchanged.

  - New `KanvazCards` functions in support of the above (general-purpose, not MCP-only): `updateCardData(id, patch)`, `setTags(id, tags)`, `deleteCardImmediate(id)`, `search(query)`, `createFileRefCardAtPath(x, y, p)`.

- **v4.6.1 (implemented this session, not yet released)** — v4.6.0's `.pur` fix was only ever tested against hand-built synthetic files. The user made a real PureRef file and live-tested it, and it still silently returned 0 images — a much worse discovery than the 4.6.0 hang, because it fails *quietly*, and this is explicitly called out as Kanvaz's "killer feature." Two more real format-assumption bugs found and fixed:
  1. **Only PNG was ever recognized** — the real file's one embedded photo was JPEG. Generalized to a format table (PNG/JPEG/GIF/BMP), scan finds whichever signature occurs earliest.
  2. **The 224-byte fixed header assumption was wrong for this PureRef version** — a real 2.1.x file has a variable-length version-string preamble instead, and the embedded image started at byte ~106, well before where the old code started scanning. Image scan now starts from byte 0 (canvas/zoom were never used in the return value anyway, so nothing depends on the header being exactly 224 bytes).
  3. **Real files interleave item/transform records BETWEEN images**, not strictly after all of them — the scanner used to shred that data into meaningless "duplicate" filler chunks while searching for the next image signature. Now stops the image scan the instant a real item marker is seen.
  4. **New defense-in-depth: grid fallback.** If transform-linking still finds zero results despite real images being present (the byte-level item layout is reverse-engineered and won't hold for every PureRef version forever), every real image now gets placed on a simple grid instead of the import coming back empty. This is what actually saved the real test file's import, not a hypothetical.
  - **Caught and fixed a genuine perf regression before it shipped**: an early version of the multi-format scan re-ran `indexOf` for every format on every iteration unconditionally, which re-introduced the exact O(n²) blowup 4.6.0 had just fixed (40,000 images regressed from ~50ms to ~51s). `test/pur-import-test.js`'s existing performance test caught this immediately — a real example of a regression test doing its job, not just theater.
  - The real test file itself is NOT a shippable fixture (personal file, real copyrighted album art) — `test/pur-import-test.js` gained a synthetic JPEG-only fixture (Test E) exercising the same code paths instead. The extracted image from the real file was independently verified by writing it back to a real `.jpg` and visually confirming correct decode.

- **v5.0.0 (implemented this session, not yet released)** — first of the new post-v4.9.0 four-feature-plus-polish arc:
  1. **Annotation resize-drift fix, finally.** Root cause confirmed by reading `annotate.js` end to end: `onUp()` stored every finished stroke's points as absolute CSS-pixel coordinates (from `getPos()`), and `redraw()` (used both live and via `loadStrokes()` on file load) replayed those same absolute numbers regardless of the card's *current* size — `resize()`'s own live bitmap-rescaling only ever touched the rendered canvas pixels in memory, never the underlying stored stroke data, so it did nothing for the save/reload case that was actually reported broken. Fix: stroke points are now stored as 0–1 fractions of the card's CSS width/height (divided at `onUp()` time, multiplied back by the card's current size in `redraw()`). Legacy absolute-pixel saves self-migrate on load — `loadStrokes()` detects any point clearly outside 0–1 (cards are never sub-2px, so this cleanly distinguishes old-format data with no explicit version flag needed) and converts it once using the card's current saved size; best-effort only for a card resized after drawing but before this fix shipped, still strictly better than the unbounded drift it replaces. Not yet manually GUI-verified (sandbox can't run Electron) — logic-verified by tracing every call site (`onUp`, `redraw`, `loadStrokes`, `resize`) by hand; `validate.js` stays clean since this code path has no existing automated test (canvas/DOM-heavy, not practical to unit test the way `pur-import-test.js` tests pure parsing logic).
  2. **URL card "Fetch preview."** New main-process `fetch-url-preview` IPC handler (`fetchUrlBuffer()` + `extractUrlMeta()` in `main.js`) does a capped (512KB) HTML fetch to read `og:title`/`<title>` and `og:image`, then a second capped (2MB) fetch for the image itself if present, returned as a `data:` URI so the card never holds a live remote image reference. Deliberately the one disclosed exception to "zero background network calls" — but still opt-in *per click*, per card, never automatic; a fetched preview (`card.urlPreview`) is saved with the board and never re-fetched on reload. Regex-based HTML parsing (two small patterns, property-then-content and content-then-property attribute order), not a full DOM parser — deliberately narrow surface for parsing arbitrary third-party HTML.
  3. **File card type-specific icon.** `fileIconLabel()` in `cards.js` derives a short label (PDF/ZIP/DOC/XLS/PPT, or the raw extension) from the path string alone — no file read, no network, updates live when "Change file" points the card at something new.

  - **8 real, confirmed bugs found and fixed, each verified by reading the actual current code (not just trusting the finder agent's report) before touching anything:**
    1. **Annotation data corruption when Map View is active** (`annotate.js`) — `getCardSize()` read `offsetWidth`/`offsetHeight` first, which is `0` for any element under a `display:none` ancestor (exactly what Map View does to the whole board while active). A pre-4.9.1 board opened while Map View happened to be open would migrate legacy stroke coordinates against a wrong fallback size and write the corruption straight back into `card.annotations` on the next save — a real, reachable, silent data-loss path. Fixed with a new `resolveCardSize()` that reads the card element's own inline `style.width`/`style.height` first (always set by `cards.js` at render/resize time, and — unlike `offsetWidth` — doesn't require layout, so it's correct regardless of visibility); applied to both `getCardSize()` and `attach()`'s own canvas-buffer-sizing fallback (which had the identical 300×200-literal problem one level up).
    2. **Legacy-stroke migration only checked a stroke's first point** (`annotate.js`'s `strokeLooksLegacy()`) — a stroke starting near a card's corner (`x1=1,y1=1`) but extending well past it was misclassified as already-normalized, skipped migration, and got double-scaled by `redraw()` into permanently wrong geometry once resaved. Fixed to check every point in a pen stroke (loop, not just index 0) and all four coordinates of a rect/arrow.
    3. **Light-theme pinned+selected card shadow broke** (`main.css`) — a genuine regression from this same arc's own v5.2.0 theme-variable cleanup: removing `.card.selected`'s light-theme `!important` (which used to unconditionally beat `.card.selected.pinned`'s higher 3-class specificity regardless of value) left `.card.selected.pinned`'s old hardcoded dark-tuned literal winning in both themes now that specificity, not `!important`, decides. Fixed by pointing `.card.selected.pinned` at the same `--shadow-card-selected` variable `.card.selected` already uses — there's nothing left to "win" once both rules agree on the same value.
    4. **`rememberedSizes`/`recentTags` (both new in v5.2.0) leaked across board switches** (`cards.js`) — module-level state with no reset tied to the actual board-transition boundary. The fix specifically does NOT hook into `clearAll()`/`deserialise()`, because those also run on every undo/redo (`history.js`'s `restore()`) — resetting there would wrongly wipe "recently used" mid-editing-session on a plain Ctrl+Z. Instead, a new `KanvazCards.resetSessionState()` is called from `boards.js`'s `newBoard()` and `loadBoardState()` specifically (the latter covers switch/open/recovery/template-restore — every real call site) — the genuine board-transition boundary, not the more general "cards array got cleared" one.
    5. **Bulk-tag via Map View flooded recent-tags with pre-existing tags** (`cards.js`'s `setTagsCore()`) — noted every tag in a card's new full tag list as "recently used," including ones the card already had. Bulk-tagging 50 cards each carrying 5 unrelated tags buried the one tag actually just typed. Fixed by diffing against the card's previous tag list first and only noting genuinely new ones.
    6. **Template Gallery fired `boardLoad` before any cards existed** (`ui.js`/`boards.js`) — `showTemplateGallery`'s "Use" handler called `KanvazBoards.newBoard(true, ...)` (which fires `boardLoad` against a still-empty board) and only populated cards afterward via a separate `deserialise()` call, unlike every other board-load path (`loadBoardState()`) which deserialises first. A plugin reacting to `boardLoad` via `getAll()` would see zero cards. Fixed by giving `newBoard()` an optional third `initialCards` argument that deserialises BEFORE the event fires — `showTemplateGallery` is the only caller using it so far.
    7. **Map View group-drag re-queried the DOM and rebuilt the connection SVG on every mousemove** (`map-view.js`) — one `document.querySelector` per selected node PLUS a full unthrottled `renderLines()` SVG rebuild, per mousemove, for the whole drag. The existing window-resize handler had already learned to `requestAnimationFrame`-coalesce this exact same `renderLines()` call (with its own comment explaining why) — the newer group-drag code just hadn't been brought in line with that lesson. Fixed: element references cached once at drag start (both the group-drag `groupDragOrigins` map and the single-node `dragNodeEl`), and a new `scheduleDragRenderLines()` coalesces the SVG rebuild through one in-flight rAF during a drag, with a final synchronous `renderLines()` call on drag-end (and the pending rAF cancelled) so the very last frame is never left stale.
    8. **Folder-drop handler blocked Electron's main process with sync I/O** (`main.js`'s `resolve-dropped-paths`) — `fs.statSync`/`fs.readdirSync` in a loop, on the same process that owns the native window's message pump — the same class of bug the v4.6.0 `.pur`-import hang was, just a smaller trigger (a large or network-drive folder instead of a large file). Fixed: rewritten with `fs.promises`, each folder's entries stat'd in parallel via `Promise.all`, same per-entry try/catch-and-skip error handling preserved exactly.

## Standing working rules for this project

1. **I never run git commands myself.** Any git action (commit/tag/push) is handed to the user as a single chained Git Bash command, always starting with `cd`, clearly labeled "Git Bash only." The user runs it in their own terminal against the same real `F:\OBL\Kanvaz` folder my sandbox mounts.
2. **Version bumps touch 6 canonical locations** (+1 non-canonical): `package.json`, `package-lock.json` (both spots), `src/boards.js` `VERSION` const, `src/ui.js` About screen (two strings), `README.md` build-output filenames, and `docs/generate_overview_pdf.py`'s version pill (this last one is NOT covered by `test/validate.js`'s automated check — verify it by hand every time).
3. **`node test/validate.js` and `node test/format-roundtrip-test.js` must both pass clean before any release is considered done.** Port-alignment will SKIP in a sandbox with no real Chrome binary — that's expected, not a failure.
4. **The website is explicitly off-limits until the user says so.** Release/CHANGELOG work happens first, website updates are a separate, deliberate, joint step — flagged in `docs/ROADMAP.md` as the natural thing to revisit once v5.0 ships.
5. **Don't guess-patch UI bugs from static code alone.** Code that looks correct on read has more than once turned out to have a real, different bug once the user clarified specifics. Ask one targeted clarifying question rather than shipping a speculative fix.
6. Kanvaz's own linter (`test/lint.js`) enforces ES5 `var`-only style, scoped to `src/` only — not `official-plugins/` or `test/`. Third-party and official plugins are NOT bound by this rule (a plugin is just a `<script>` tag).
7. **Resolved in 4.4.0** (kept here for history, not as an open item anymore): MCP Bridge's local-listener capability got its own new `server` permission rather than extending `network` — genuinely different in kind (inbound vs. outbound), and it's the ONE permission that's actually enforced today (see "Where things stand technically"). If a future plugin needs real outbound network or filesystem access, decide then whether to build the same kind of real enforcement for `network`/`fs` or keep them informational-only — don't assume either default without asking, since "build it because the manifest vocabulary already lists it" was explicitly rejected this pass as not worth the added surface area until something actually needs it.
8. **When handing the user a shell command, match their actual shell.** This project's convention is "Git Bash only" for git actions (see rule #1), but confirm that's genuinely where they're pasting it if there's any signal otherwise (e.g. a `PS C:\...>` prompt in their own pasted output means PowerShell, where `&&` is invalid pre-7.0) — a command that silently fails to chain can look like partial success (some commands ran, `&&`-gated ones after the failure didn't) rather than an obvious error, which is exactly what caused the v4.3.0 tag-mispoint incident above.
9. **Before calling any significant feature done, run the multi-lens audit pass documented in `docs/AUDIT_METHODOLOGY.md`.** Not a one-off for v4.4.0 — a standing practice, explicitly requested to keep happening every time (parallel independent reviewers each with a distinct lens, cross-verified findings, root-cause fixes, regression tests actually verified to catch what they claim to, honest disclosure of anything not fully fixable). "Significant" means: new IPC surface, new permission/trust boundary, anything MCP Bridge touches, or anything else that would get its own CHANGELOG section.
